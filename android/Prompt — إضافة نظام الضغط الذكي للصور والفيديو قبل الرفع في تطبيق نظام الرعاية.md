# مهمة تطوير: إضافة Smart Media Compression قبل رفع الصور والفيديو

أنت تعمل على مشروع Android Hybrid App باسم **«نظام الرعاية»**، مبني على:

- PWA / WebView + Vite
- Capacitor
- Android Native Java
- WorkManager
- SQLite
- IndexedDB
- OkHttp
- Laravel API
- Chunked Upload
- Background Upload
- Google Drive / Server Storage

راجع الكود الحالي أولًا، ولا تفترض أسماء ملفات أو Classes غير موجودة. حافظ على البنية الحالية ولا تعيد بناء نظام الرفع أو المزامنة من الصفر.

---

## 1. الهدف الرئيسي

إضافة نظام **Smart Media Compression** يقوم بضغط وتحسين الصور والفيديو **محليًا على جهاز Android قبل إدخال الملف إلى طابور الرفع وقبل بدء أي اتصال لرفع الملف**.

الهدف:

- تقليل استهلاك الإنترنت.
- تسريع الرفع.
- تقليل مساحة التخزين على السيرفر.
- الحفاظ على أعلى جودة بصرية ممكنة.
- عدم تحميل الملفات الكبيرة بالكامل إلى RAM.
- عدم التأثير على نظام Chunked Upload الحالي.
- عدم التأثير على المزامنة الحالية.

---

# 2. التدفق المطلوب

غيّر تدفق رفع الوسائط ليصبح:

```text
Camera / Gallery / File Picker
             ↓
      حفظ الملف محليًا
             ↓
     قراءة إعداد الضغط الذكي
             ↓
       هل الضغط مفعّل؟
          /       \
        نعم        لا
        ↓           ↓
SmartMediaProcessor Original File
        ↓           ↓
        └─────┬─────┘
              ↓
       فحص الملف النهائي
              ↓
        Upload Queue
              ↓
      ChunkedUploadWorker
              ↓
             Upload
```

مهم جدًا:

**عند تفعيل الضغط، يجب ألا يدخل الملف الأصلي إلى طابور الرفع.**

الملف الأصلي يمكن الاحتفاظ به مؤقتًا أثناء المعالجة، ثم حذف النسخة المؤقتة حسب سياسة التخزين.

---

# 3. إنشاء طبقة مستقلة

أنشئ Native component مستقل باسم مناسب مثل:

```text
SmartMediaProcessor
```

أو استخدم بنية المشروع الحالية إذا كان هناك Processor/Media Service موجود أصلًا.

المكوّن مسؤول عن:

- تحديد نوع الملف.
- فحص الحجم.
- ضغط الصور.
- ضغط الفيديو.
- إزالة Metadata غير الضرورية.
- إنشاء نسخة مؤقتة محسنة.
- مقارنة الحجم الأصلي بالحجم النهائي.
- اختيار النسخة الأفضل.
- إرجاع مسار الملف النهائي للـ Upload Queue.

لا تجعل `ChunkedUploadWorker` مسؤولًا عن الضغط.

---

# 4. إعداد الضغط الذكي

أضف إعدادًا داخل التطبيق:

```text
الضغط الذكي قبل الرفع
[ ON / OFF ]
```

الوصف:

> يقوم التطبيق تلقائيًا بتقليل حجم الصور والفيديو قبل رفعها مع الحفاظ على أعلى جودة بصرية ممكنة.

القيمة الافتراضية:

```text
ON
```

احفظ الإعداد محليًا باستخدام آلية إعدادات Android الحالية في المشروع.

لا تنشئ نظام Preferences جديدًا إذا كان هناك نظام إعدادات موجود.

مثال منطقي:

```text
smart_compression_enabled = true
```

---

# 5. إعدادات منفصلة للصور والفيديو

إذا كانت واجهة الإعدادات تسمح، أضف:

```text
الضغط الذكي قبل الرفع        ON

ضغط الصور                    ON
ضغط الفيديو                  ON
```

إذا لم يكن من المناسب إضافة إعدادين منفصلين حاليًا، اجعل الزر الرئيسي يتحكم بالاثنين، لكن صمّم الكود بحيث يمكن فصل الإعدادين مستقبلًا.

---

# 6. ضغط الصور

عند اختيار صورة:

1. قراءة حجم الملف.
2. قراءة أبعاد الصورة.
3. قراءة MIME Type.
4. عدم تحميل الصورة كاملة إلى RAM إذا كان حجمها كبيرًا.
5. إزالة Metadata غير الضرورية.
6. المحافظة على Orientation.
7. عدم تغيير الأبعاد إذا كانت مناسبة.
8. إذا كانت الصورة ضخمة جدًا، يمكن تقليل أبعادها إلى حد منطقي.
9. استخدام JPEG/WebP حسب أفضل خيار مدعوم في المشروع والجهاز.
10. استخدام جودة عالية.
11. إنشاء ملف مؤقت.
12. مقارنة حجم الملف الجديد بالأصلي.

---

# 7. قواعد ضغط الصور

لا تستخدم ضغطًا مبالغًا فيه.

المبدأ:

```text
Quality First
```

وليس:

```text
Maximum Compression
```

ابدأ بجودة عالية تقريبًا:

```text
85 - 90%
```

ثم اختبر النتائج.

لا تقم بتقليل دقة صورة صغيرة.

مثال:

```text
1200x1600
```

لا يجب تحويلها إلى:

```text
640x480
```

لمجرد تقليل الحجم.

أما الصور شديدة الضخامة، فيمكن وضع حد أقصى مناسب للأبعاد، مثل:

```text
MAX_DIMENSION = 1920 أو 2560
```

لكن اجعل هذه القيمة قابلة للتعديل في Configuration وليس hard-coded في عدة أماكن.

---

# 8. إزالة Metadata

عند إنشاء النسخة المضغوطة، أزل البيانات غير الضرورية مثل:

- GPS
- Camera Make
- Camera Model
- Software
- Author
- Comments
- Device information

مع المحافظة على البيانات اللازمة لعرض الصورة بشكل صحيح، خصوصًا:

```text
Orientation
```

لا تؤثر على الصورة نفسها أو تقص أي جزء منها.

---

# 9. لا تضغط الملفات الصغيرة بلا فائدة

أضف حدًا أدنى للحجم.

مثلًا:

```text
MIN_COMPRESSION_SIZE = 1 MB
```

إذا كان الملف أصغر من الحد:

```text
استخدم الملف الأصلي
```

ولا تنفذ عملية ضغط غير ضرورية.

---

# 10. اختيار النسخة الأفضل

بعد الضغط:

```text
originalSize
compressedSize
```

إذا كان:

```text
compressedSize >= originalSize
```

استخدم الأصل.

إذا كان:

```text
compressedSize < originalSize
```

استخدم النسخة المضغوطة.

لا ترفع النسختين.

---

# 11. ضغط الفيديو

يجب معالجة الفيديو بطريقة Streaming / File Based.

ممنوع:

```text
read entire video into byte[]
```

أو أي أسلوب يؤدي إلى تحميل فيديو 200MB أو 500MB أو 1GB بالكامل إلى RAM.

استخدم Encoder/Transcoder مناسبًا لنظام Android والمكتبات الموجودة في المشروع.

يمكن استخدام Android MediaCodec / MediaExtractor / MediaMuxer أو مكتبة موثوقة موجودة بالمشروع حسب حالة المشروع الحالية.

لا تضف مكتبة ضخمة إذا كانت هناك آلية native مناسبة.

---

# 12. قواعد ضغط الفيديو

الأولوية:

1. الحفاظ على الدقة.
2. الحفاظ على FPS.
3. الحفاظ على الصوت.
4. تقليل Bitrate.
5. تقليل الحجم.
6. عدم تدمير الجودة.

مثال:

```text
1920x1080
30 FPS
```

يفضل أن يبقى:

```text
1920x1080
30 FPS
```

مع تخفيض Bitrate بدل تحويله مباشرة إلى 720p.

يمكن الانتقال إلى خفض الدقة فقط عندما يكون الفيديو ضخمًا جدًا أو Bitrate مرتفعًا بشكل غير منطقي.

---

# 13. Video Codec

افحص دعم الجهاز.

يمكن استخدام:

```text
H.264
```

كخيار توافق أساسي.

ويمكن استخدام:

```text
H.265 / HEVC
```

عندما يكون الجهاز والـ backend والتطبيق قادرين على التعامل معه.

لا تجعل H.265 إلزاميًا إذا كان سيؤدي إلى مشاكل توافق.

---

# 14. الحفاظ على الصوت

الفيديو المضغوط يجب أن يحتفظ بالصوت.

يجب الحفاظ قدر الإمكان على:

- Audio Track
- Sample Rate
- Channels

وإذا تمت إعادة ترميز الصوت، استخدم إعدادًا عالي الجودة.

---

# 15. فيديو صغير

لا تضغط الفيديو إذا كان صغيرًا ولا يوجد فائدة حقيقية.

مثال:

```text
Original = 8 MB
Compressed = 7.8 MB
```

لا تستخدم النسخة المضغوطة.

استخدم الأصل.

---

# 16. الملفات الكبيرة جدًا

عند التعامل مع:

```text
100 MB
500 MB
1 GB+
```

يجب:

- عدم تحميل الملف كاملًا في RAM.
- استخدام ملفات مؤقتة.
- استخدام Streaming.
- مراقبة المساحة الحرة.
- إلغاء المعالجة عند امتلاء التخزين.
- تنظيف الملفات المؤقتة بعد النجاح أو الفشل.
- عدم ترك ملفات مؤقتة يتيمة.

---

# 17. المساحة الحرة

قبل بدء ضغط فيديو كبير:

افحص:

```text
Available Storage
```

إذا لم توجد مساحة كافية لإنشاء نسخة مؤقتة:

- لا يبدأ الضغط.
- يتم تسجيل السبب.
- يمكن استخدام الأصل إذا كانت سياسة التطبيق تسمح.
- لا يحدث Crash.

---

# 18. واجهة المستخدم

عند رفع صورة أو فيديو كبير، أظهر حالة واضحة:

```text
جاري تجهيز الملف...
```

ثم:

```text
جاري تحسين الصورة...
```

أو:

```text
جاري ضغط الفيديو...
```

ثم:

```text
تم تحسين الملف
```

مثال:

```text
الحجم الأصلي: 86.4 MB
الحجم بعد الضغط: 31.7 MB
تم توفير: 63%
```

ثم:

```text
جاري الرفع...
```

---

# 19. Progress

أثناء ضغط الفيديو، يجب إظهار Progress إذا كان من الممكن الحصول عليه.

مثال:

```text
ضغط الفيديو
████████████░░░░ 72%
```

ثم:

```text
تم الضغط بنجاح
```

بعد ذلك يبدأ Upload Progress الموجود حاليًا.

لا تخلط:

```text
Compression Progress
```

مع:

```text
Upload Progress
```

---

# 20. تعديل Upload Queue

عند نجاح المعالجة:

يجب أن يدخل إلى:

```text
upload_queue
```

مسار الملف النهائي فقط.

يمكن إضافة Metadata للعنصر:

```text
original_size
processed_size
compression_enabled
compression_type
compression_ratio
```

مثال:

```text
original_size = 86400000
processed_size = 31700000
compression_enabled = true
compression_type = video
compression_ratio = 63.3
```

إذا لم تتم المعالجة:

```text
compression_enabled = false
```

---

# 21. عدم كسر ChunkedUploadWorker

يجب ألا يتم تغيير منطق:

```text
ChunkedUploadWorker
```

إلا إذا كان ضروريًا.

بعد إنشاء الملف النهائي، يجب أن يتعامل معه النظام الحالي كأي ملف عادي.

يستمر:

```text
fetchReceivedChunks
```

واستئناف الرفع.

ويستمر:

```text
8KB streaming
```

أو آلية Streaming الحالية.

لا تعيد بناء نظام Chunked Upload.

---

# 22. WorkManager

لا تجعل الضغط داخل Worker الرفع إذا كان ذلك سيؤثر على النظام الحالي.

الأفضل:

```text
PrepareUploadsWorker
       ↓
SmartMediaProcessor
       ↓
Upload Queue
       ↓
ChunkedUploadWorker
```

أو دمجه داخل `PrepareUploadsWorker` إذا كانت البنية الحالية مناسبة.

لكن يجب أن يبقى منطقيًا:

```text
Prepare
→ Compress
→ Queue
→ Upload
```

وليس:

```text
Upload
→ Compress
```

---

# 23. التعامل مع إغلاق التطبيق

إذا تم إغلاق التطبيق أثناء ضغط فيديو:

- يجب ألا يترك النظام حالة upload غير صحيحة.
- يجب تسجيل حالة المعالجة.
- عند إعادة التشغيل يتم اكتشاف الملفات المؤقتة أو المهام غير المكتملة.
- يتم تنظيف الملفات القديمة.
- يمكن إعادة المعالجة عند الحاجة.

أضف حالات واضحة مثل:

```text
PENDING
PROCESSING
PROCESSED
UPLOAD_PENDING
UPLOADING
COMPLETED
FAILED
```

---

# 24. فشل الضغط

إذا فشل الضغط:

لا تجعل التطبيق ينهار.

سجّل الخطأ.

مثال:

```text
Compression failed
reason = ...
```

ثم حسب السياسة:

```text
Use Original File
```

إذا كان الملف الأصلي صالحًا.

لكن إذا كان إعداد المستخدم يتطلب عدم رفع أي ملف بدون ضغط، فاعرض الخطأ بدل رفع الأصل.

اجعل هذا السلوك Configuration واضحًا.

الافتراضي المقترح:

```text
Fallback to original = true
```

---

# 25. حذف الملفات المؤقتة

بعد نجاح تجهيز الملف:

- احذف الملفات المؤقتة غير المستخدمة.

بعد نجاح الرفع:

- احذف نسخة الضغط المؤقتة إذا لم تعد مطلوبة.

عند الفشل:

- لا تحذف ملفًا مطلوبًا لإعادة المحاولة.
- نظف الملفات المؤقتة غير المرتبطة بأي Queue Item.

أضف Cleanup Worker إن كان مناسبًا.

---

# 26. JavaScript Bridge

إذا احتاجت الواجهة إلى التحكم في الإعداد، أضف Bridge مثل:

```text
window.AndroidBridge.setSmartCompressionEnabled(true)
window.AndroidBridge.isSmartCompressionEnabled()
```

أو استخدم Capacitor Plugin إذا كان ذلك هو الأسلوب القياسي في المشروع.

لا تضف Bridge جديدًا إذا كان هناك Plugin مناسب بالفعل.

---

# 27. IndexedDB

يجب أن تكون حالة الملف متوافقة بين:

```text
IndexedDB
```

و:

```text
SQLite upload_queue
```

عند تغيير الملف من الأصل إلى النسخة المضغوطة، يجب تحديث المسار/الحجم/الحالة بشكل ذري قدر الإمكان.

لا تجعل IndexedDB يشير إلى ملف تم حذفه.

---

# 28. الإحصائيات

يمكن تحديث الواجهة لإظهار:

```text
الملفات التي تم تحسينها
إجمالي الحجم قبل الضغط
إجمالي الحجم بعد الضغط
إجمالي الحجم الذي تم توفيره
```

مثال:

```text
تم تحسين 25 ملفًا
قبل: 1.8 GB
بعد: 720 MB
التوفير: 1.08 GB
```

هذه الميزة اختيارية إذا كانت تتطلب تعديلات كبيرة.

# 29. الخصوصية

إزالة Metadata يجب أن تتم قبل الرفع.

خصوصًا:

```text

Device Metadata
Camera Metadata
Author
Comments
```

بحيث لا يتم إرسال هذه البيانات للسيرفر عند استخدام الضغط الذكي.

```text
WebContentsDebugging
```

لا تؤثر الميزة على Authentication أو Token أو WebSocket.

# 32. حالات الاختبار

أنشئ اختبارات للحالات التالية:

### صورة صغيرة

```text
500 KB
```

النتيجة:

```text
لا ضغط
```

### صورة كبيرة

```text
8 MB
```

النتيجة:

```text
ضغط → ملف أصغر
```

### PNG

اختبر تحويلها فقط إذا كان ذلك آمنًا ولا يسبب فقدًا غير مقبول.

### صورة Orientation

اختبر الصور الملتقطة بالهاتف بالطول.

يجب ألا تصبح مقلوبة بعد الضغط.

### فيديو صغير

```text
10 MB
```

لا ضغط إذا لم توجد فائدة.

### فيديو 1080p

اختبر:

```text
1920x1080
30 FPS
```

### فيديو كبير

```text
500 MB+
```

يجب ألا يحدث:

```text
OutOfMemoryError
```

### انقطاع الإنترنت

يجب أن يبقى الملف المضغوط في Queue ويُرفع لاحقًا.

### إغلاق التطبيق أثناء الضغط

لا يحدث Crash.

### إعادة تشغيل الهاتف

يجب استعادة حالة الملفات.

### الضغط OFF

يجب رفع الأصل كما هو.

### الضغط ON

يجب ألا يتم رفع الأصل.

# 33. Logging

أضف Logs واضحة، لكن لا تسجل:

- Access Tokens
- كلمات المرور
- بيانات شخصية حساسة

مثال:

```text
[SmartMedia] Processing started
[SmartMedia] Type=video
[SmartMedia] Original=86400000
[SmartMedia] Processed=31700000
[SmartMedia] Saved=63.3%
[SmartMedia] Queueing processed file
```

# 34. الأداء

الهدف ليس فقط تقليل الحجم.

يجب أيضًا:

- عدم استهلاك RAM بشكل خطير.
- عدم تجميد UI.
- تنفيذ المعالجة في Background.
- عدم إيقاف المزامنة.
- عدم إيقاف WebSocket.
- عدم التأثير على Upload Queue.

---

# 35. لا تغير النظام الحالي بلا داعٍ

قبل تعديل أي شيء:

1. افحص المشروع.
2. ابحث عن جميع نقاط دخول الصور والفيديو.
3. ابحث عن:
   - Camera
   - Photo
   - Gallery
   - File Picker
   - Upload Queue
   - PrepareUploadsWorker
   - ChunkedUploadWorker
   - UploadTaskScheduler
   - UploadDatabaseHelper
4. حدد أفضل نقطة لإدخال `SmartMediaProcessor`.

لا تنشئ Duplicate Upload System.

لا تنشئ Database جديدة.

لا تنشئ نظام Queue جديد.

استخدم الأنظمة الحالية.

```text
        ↓

        ↓

        ↓

```

```text

        ↓
```

# 37. شرط أساسي

**لا ترسل الملف الأصلي للسيرفر قبل انتهاء المعالجة.**

عندما يكون:

```text
smart_compression_enabled = true
```

يجب أن يكون الملف الذي يصل إلى:

```text
upload_queue
```

هو الملف النهائي المعالج فقط.

## النتيجة المطلوبة

أريد ميزة إنتاجية Production Ready وليست Prototype.

يجب أن تكون:

- مستقرة.
- سريعة.
- قليلة استهلاك الذاكرة.
- تعمل Offline.
- تعمل مع WorkManager.
- تعمل مع النظام الحالي للرفع المجزأ.
- لا تكسر المزامنة.
- لا تكسر WebSocket.
- لا تكسر IndexedDB.
- لا تكسر SQLite.
- لا ترفع الأصل عند تفعيل الضغط.
- تحافظ على جودة الصور والفيديو قدر الإمكان.
- تنظف Metadata غير الضرورية.
- تتعامل مع الملفات الكبيرة بأمان.
