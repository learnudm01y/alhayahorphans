# 13 — إصلاح شاشة التسجيل (registration.html): المرفقات / التحقق / جلب بيانات السجل المدني

⚠️ `registration.html` من الملفات **المحمية غير المُلمَسة** حسب كتالوج 08 — أي إصلاح هون يجب أن يبقى **إضافة/تصحيح دقيق مستهدف**، لا إعادة كتابة الملف. كل قسم أدناه: تشخيص أولاً (أوامر فحص) ثم إصلاح مشروط بنتيجة التشخيص.

## أ. مشكلة المرفقات

### تشخيص
```bash
# 1) هل عملية الرفع المجزأ نفسها شغالة أساساً (منفصلة عن v4 بالكامل)؟
mysql -u root -p -e "SELECT status, COUNT(*) FROM aso.chunked_uploads GROUP BY status ORDER BY COUNT(*) DESC LIMIT 10;"
# لو أغلب الحالات 'failed' أو 'stuck' = مشكلة أساسية بالرفع المجزأ نفسه، غير مرتبطة بـ v4

# 2) هل جدول attachments يستقبل سجلات جديدة فعلياً بعد التسجيل؟
mysql -u root -p -e "SELECT MAX(created_at), COUNT(*) FROM aso.attachments WHERE created_at > NOW() - INTERVAL 7 DAY;"
```
```
# على الجهاز: راقب أثناء تجربة رفع مرفق فعلي بشاشة التسجيل
adb logcat | grep -iE "upload|chunk|attachment"
```

### الاحتمالات الأكثر ترجيحاً (حسب مصدرها بالمعمارية)
| إذا شفت بالفحص | السبب المرجَّح | الإصلاح |
|------------------|-------------------|---------|
| رفع ناجح بـ `chunked_uploads` لكن المرفق ما بيظهر بالفهرسة الجديدة (`file_index_v4`) | متوقَّع ومقصود — `file_index_v4` تُبنى بمزامنة دورية لاحقة (الملف 03)، مو فورية عند الرفع. **مش خلل**، لكن ممكن نضيف تحديث فوري لـ`file_index_v4` مباشرة بعد نجاح كل رفع بدل انتظار الدورة القادمة (تحسين بسيط بـ`ChunkedUploadWorker` أو hook جديد بعد نجاح الرفع) | إضافة استدعاء `insertOrUpdateFileIndexEntry()` مباشرة بعد `Result.success()` بالـ Worker |
| أخطاء `Checksum mismatch` أو `Exponential Backoff` متكررة باللوج | مشكلة شبكة/حجم ملف، غير متعلقة بـ v4 إطلاقاً | فحص حجم الملفات المرفوعة وثبات الشبكة الميدانية |
| المرفق يُرفَع لكن مربوط بـ `source_id` خاطئ أو `NULL` بجدول `file_index_v4` | عمود `client_uuid` الجديد بجدول `attachments`؟ **لاحظ:** جدول `attachments` لم يُذكَر بقائمة الجداول الستة اللي أخذت أعمدة v4 (الملف 04) — تأكد هل `attachments` فعلاً محتاج نفس المعالجة | إذا مؤكَّد، migration إضافية بنفس نمط الملف 06 لإضافة `client_uuid` لجدول `attachments` أيضاً |

## ب. مشكلة التحقق (Validation)

### تشخيص
```bash
# سجلات فشل الـ 422 Validator خلال آخر أسبوع
tail -n 2000 storage/logs/laravel.log | grep -B2 "ValidationException\|422" | tail -n 100
```
```
# على الجهاز: افتح Developer Tools على WebView (chrome://inspect من كمبيوتر متصل بنفس الشبكة)
# وحاول تسجيل مع بيانات فيها الحقل المشكوك فيه، راقب Network tab لرد الـ 422 وتفاصيله بالـ response body
```

### الاحتمالات الأكثر ترجيحاً
| إذا شفت بالفحص | السبب المرجَّح | الإصلاح |
|------------------|-------------------|---------|
| رسالة 422 تذكر حقل `client_uuid` أو `sync_origin_device_id` أو `needs_review` | **الأرجح تماماً** — `registration.html`/`MobileRegistrationController` (القديم) لا يعرف بوجود هذه الأعمدة الجديدة، لكن لو الـ Validator القديم يستخدم `$request->validate([...])` بقائمة صريحة (whitelist) وبيحاول يمرر هالحقول الجديدة كـ unexpected أو بالعكس بيتوقع حقل مو موجود، ممكن يطلع خطأ. **لكن الأصل:** الكود القديم ما لازم يعرف بهاي الأعمدة أصلاً لأنها nullable وما حدا طالبها. تحقق: هل فعلاً `MobileRegistrationController::store` بيحدد أعمدة INSERT صراحة (`Data::create(['field1'=>...])` محدودة) أم `$request->all()`؟ لو محدودة، هاي الأعمدة الجديدة ما لازم تأثر إطلاقاً | لو التأثير مؤكَّد فعلياً (نادر لكن ممكن لو الكود يعمل `array_keys($validated) === array_keys($request->all())` أو ما شابه) — الإصلاح **لا يلمس الكود القديم** (محظور)، بل نتأكد الـ Trigger ما يتعارض مع أي `strict mode` بـ MySQL. جرّب: `SET SESSION sql_mode = '';` مؤقتاً واختبر مرة ثانية لعزل السبب |
| رسالة 422 لا علاقة لها بأعمدة v4 إطلاقاً (حقل تاريخ، رقم هوية، إلخ) | مشكلة أصلية موجودة من قبل v4 بالكامل، غير مرتبطة بمشروعنا | تُوثَّق كخلل منفصل خارج نطاق خطة v4 (يحتاج تعديل ملف قديم = خارج المبدأ الحاكم، إلا بموافقة صريحة استثنائية) |
| Validation يفشل **فقط** بعد آخر تحديث DB (migration 000001/000002) وليس قبله | تأكيد قوي إنه السبب من التريغرز/الأعمدة الجديدة | افحص فوراً: `SHOW TRIGGERS FROM aso;` وتأكد التريغرز الستة موجودة بس على الجداول الستة المحدَّدة، وما في أي تأثير جانبي على validation logic بـ Laravel (التريغرز بمستوى DB فقط، ما لازم تلمس Laravel validation إطلاقاً نظرياً) |

## ج. مشكلة جلب بيانات السجل المدني والبيانات المخزَّنة بقاعدة البيانات

هذا الجزء غالباً يشمل وظيفتين مختلفتين بشاشة التسجيل:
1. **البحث برقم الهوية لجلب بيانات موجودة مسبقاً** (`BackgroundSyncPlugin.getDataByIdNumber` من `related_data.db` — Offline محلي بالكامل).
2. **جلب بيانات من السجل المدني** (`CivilRegistryStore.getPerson()` من ملفات `.gz` محلية مبنية من قاعدة `civilregistry` المنفصلة).

### تشخيص — الجزء 1 (البحث المحلي `related_data.db`)
```
adb logcat | grep -iE "getDataByIdNumber|related_data|BackgroundSyncPlugin"
```
```bash
# هل related_data.db بالسيرفر (لو فيه نسخة مرجعية) محدَّثة أصلاً؟ أهم سؤال: متى آخر مزامنة كاملة صارت لهالقاعدة تحديداً على الأجهزة؟
# هذا يتطلب فحص ميداني مباشر على الجهاز (via adb) وليس عبر السيرفر
adb shell run-as com.aso.app ls -la /data/data/com.aso.app/databases/related_data.db
```

```

```

### الاحتمالات الأكثر ترجيحاً
| إذا شفت بالفحص | السبب المرجَّح | الإصلاح |
|------------------|-------------------|---------|
| `related_data.db` على الجهاز قديمة جداً (آخر تعديل قبل أسابيع) | محرّكا المزامنة القديمان (v3) توقفا فعلياً أو بيفشلان بصمت — **هذا بالضبط المشكلة الجذرية اللي خطة v4 كلها مبنية لحلها** (الملف 02) | تسريع تفعيل `UnifiedSyncOrchestratorV4` على هالجهاز تحديداً (بدل انتظار جدول المراحل)، لأنه v4 يسحب لنفس نوع البيانات بمصدر موحَّد وأحدث |
| السجل المدني ما بيرجع نتيجة لأرقام هوية موجودة فعلياً بقاعدة `civilregistry` | الـ Chunks (`.gz`) ما اكتملت تحميلها على الجهاز (`Error Handling` بالوثيقة الأصلية بيذكر "التحقق من اكتمال تحميل الـ Chunks قبل البحث" — يعني لو ناقصة، النظام **مصمَّم يرفض البحث بصمت** بدل يرجع نتيجة جزئية خاطئة) | تحقق من اكتمال تحميل الـ manifest بالكامل على الجهاز، أعد تشغيل `GET /api/mobile/civil-registry/manifest` يدوياً إذا لزم |
| السجل المدني يرجع بيانات **قديمة/خاطئة** (لا يرجع "ما موجود"، بل يرجع بيانات غلط) | احتمال تعارض إصدار الـ manifest المحلي مع نسخة السيرفر الحالية (`civilregistry` انضاف لها بيانات جديدة و`manifest` المحلي ما تحدَّث) | فحص `version`/`timestamp` بالـ manifest المحلي مقابل السيرفر — يحتاج آلية تحديث تزايدي، غير موجودة حالياً بالتصميم الأصلي لـ `CivilRegistryStore` (فجوة أصلية بـ v3، خارج نطاق v4 إلا لو قررت نضيفها كتحسين v4) |

### الإصلاحات المُنفَّذة (تحسينات مشروطة بالتشخيص — بدون لمس `registration.html`)

1. **فهرسة فورية بعد نجاح الرفع** (الاحتمال الأول بجدول §أ — كان الـ file_index ينتظر الدورة القادمة):
   - `ChunkedUploadWorker` — بعد `STATUS_COMPLETED` في `drainOfflineInbox` → `AdminOfflineDataStoreV4.upsertFileIndexEntry(...)`
   - `DriveStatusWorker` — نفس الاستدعاء بعد إتمام المعالجة على الخادم
   - هذا يمنع فجوة «المرفق موجود لكن غير مرئي بالفهرسة حتى الدورة التالية»

2. **`ProfilePhotoSyncManagerV4`** (ملف 11) يحمّل `cache_priority='profile_photo'` في كل دورة — يضمن ظهور الصور الشخصية أوفلاين حتى لو كان باقي الفهرس on-demand.

### ما يبقى خارج نطاق v4 (backlog منفصل — يحتاج موافقة)

- إنشاء seed data لجداول التصنيفات الفارغة (بيئة التطوير فقط).
- إضافة incremental update لـ `CivilRegistryStore` manifest (فجوة v3 أصلية — راجع §ج).
- أي تعديل فعلي على `registration.html` إذا ظهر خلل ميداني على جهاز حقيقية بعد المرحلة 6.

## الخطوة التالية (ميداني — المرحلة 6)

على جهاز حقيقي متصل بالإنتاج:
1. افتح شاشة التسجيل، ارفع مرفقاً فعلياً → تحقق أن `file_index_v4` يمتلئ **فوراً** (لا بعد دورة مزامنة).
2. `adb logcat | grep -iE "upload|chunk|attachment"` أثناء الرفع.
3. سجّل مع بيانات فيها حقل تاريخ/هوية → راقب Network tab لأي 422 (لم نرَ أي واحد محلياً).
4. `adb shell run-as com.aso.app ls -la /data/data/com.aso.app/databases/related_data.db` بعد مزامنة كاملة.
